这是什么机制

模型的上下文窗口是硬约束：一次能看的 token 有上限。更麻烦的是，就算没超限，中间位置的信息也容易被忽略——把一切塞进 prompt，从来不是「保险」的做法。

多轮 Agent 任务里，历史会不断堆积。你必须在每一步决定：这条留原文、压成摘要、还是直接丢掉。这三种操作对应真实系统的三种手段：保留原始消息、做摘要或抽取、以及驱逐（evict）。

关键在于：压缩是有损的。摘要能留住「有这件事」，但会丢掉具体数字。而排障恰恰是数字决定结论的场景。

你能学到什么

  • 你会看到占位最大的信息往往最没用：一顿午饭的讨论占 8 格，一段关键日志占 6 格——但只有后者能定根因。
  • 你会亲手体会压缩的代价是延迟结算的：压缩的那一刻很划算，等到提问时才发现数字没了。
  • 你会看到噪音会挤掉证据：预算就那么多，留下的每格闲聊都等于从证据里扣掉一格。
  • 你会明白为什么成熟的 Agent 要配外部记忆 + 检索：不是把一切塞进 prompt，而是需要时再去取。

玩法规则

  1. 预算是 24 格，信息分 4 轮进来，每轮 2~3 条。
  2. 每条信息三选一：保留原文（占满 size 格）、压缩（占 ⌈size/3⌉ 格，丢失细节）、丢弃（不占格）。
  3. 预算不足时无法加入新内容，必须先压缩或移除窗口里已有的条目。
  4. 过程中和结尾共 3 道题，答案需要窗口里的证据支撑。

算分方式

  • 每题 20 分，满分 60。
  • 答对且证据完整 = 20 分（有据可依）；答对但证据缺失 = 10 分（蒙对）；答错 = 0 分。
  • 复盘会给出预算峰值占用、噪音占比、关键证据丢失数——分数相同但指标不同，说明你的策略不同。

想深一点

试试两个极端：全部保留原文，和全部压缩成摘要。你会发现两边都拿不到满分——一个被预算卡死，一个被细节缺失卡死。中间那条线，就是你真正要设计的上下文策略。
