这是什么机制

自回归解码是串行的：每生成一个 token，都要跑一次完整的前向。GPU 在这个过程里其实很闲——它在等显存把权重搬过来，算力大量空转。

投机采样的思路是：让一个便宜的小模型（draft）先连续猜 k 个 token，再让大模型（target）一次前向并行验证这 k 个位置。从第一个猜错的地方截断，前面猜对的部分直接采信，被拒的位置由 target 自己重新采一个。

关键性质：它的输出分布和「target 单独逐 token 解码」完全一致。因为拒绝时不是简单丢弃，而是从残差分布 max(0, p_target − p_draft) 里重新采样。所以这是精确加速，不是拿质量换速度。

你能学到什么

  • 你会看到 k 不是越大越好。第一反应都是「猜长一点更快」，玩两局你会发现最优点在 2~4。
  • 你会看到接受率决定一切：每多猜一位，命中概率是乘起来的，k 越大，后面几位越是纯浪费。
  • 你会亲手把 draft 和 target 的差距调大，然后发现最优 k 直接塌到 1——这就是为什么实践中 draft 模型必须和 target 同源、同词表。
  • 你会明白拒绝的代价是时间，不是质量：被拒之后 target 重采样，出来的仍然是那个正确的词。

玩法规则

  1. 选一个难度（决定 draft 有多像 target），再选每轮猜测长度 k。
  2. 点「验证一轮」：draft 沿着自己的分布连猜 k 个 token，target 逐个判定接受或拒绝。
  3. 判定规则：接受概率 = min(1, p_target / p_draft)，比较对象是一个固定的随机数 u。被拒即截断，该位置由 target 重采样一个词。
  4. 一轮至少推进 1 个 token，直到整句 39 个 token 生成完毕。

算分方式

  • 基线：逐 token 解码，39 个 token 耗时 39 个单位。
  • 验证一轮的耗时 = 1 + 0.05k + 0.004k²。前两项是「并行验证 k+1 个位置的线性开销」，平方项是长序列下 attention 与 kernel 效率下降的近似。
  • 加速比 = 39 ÷ 总耗时。小于 1 表示你比老老实实逐 token 生成还慢。

想深一点

如果 draft 和 target 完全一样，k 应该取多大？如果 draft 完全是随机的，k 又该取多大？想清楚这两个极端，你就知道线上系统为什么要按场景动态调 k，而不是设一个固定值。
