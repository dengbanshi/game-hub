这条链路在讲什么

Agent 不是「更聪明的模型」，是一个带循环的提示词。模型本身还是那个一次前向出一段文本的东西，循环是外面这层代码给的：想 → 调工具 → 看结果 → 再想。

这个图解用一个具体的提问走完一整轮：从组装提示词、检查上下文预算，到两次 Thought / Action、RAG 检索、上下文压缩，最后给出回答。13 步，可以来回翻，也可以拧参数。

你能看出什么

  • 上下文里大部分是固定开销：系统提示 + 工具定义 + 记忆 + 历史，加起来是用户问题的一百多倍。你以为在问一句话，其实在发几千个 token。
  • 工具结果是原样回灌的。一次日历查询就带回 480 个 token，一段文档节选能带回 1000 多——上下文是被观察结果撑爆的，不是被对话撑爆的。
  • 压缩策略没有通用最优。把这段问题调成「压成摘要」，你会发现它恰好吃掉了「为什么没选另一个」的那半句——摘要丢的总是细节，而细节往往正是你问的东西。
  • 循环有三个退出条件：模型觉得够了、轮数到顶、预算耗尽。把「最大轮数」调到 2，回答会突然变得没头没尾。
  • 关掉 RAG，结论不会变成空的——它会编一个。这是这个图解里最值得记住的一屏。

怎么操作

  1. 点顶部流程图里的任意一步，或按 ← → 前后翻。
  2. 下方「调一调」是这一步真正起作用的参数。预算、RAG 开关、最大轮数、压缩策略会在好几步里同时生效。
  3. 参数会被记住。建议的读法：先把预算调到 32k，走一遍；再调到 4k，走一遍——同一段流程，两套完全不同的命运。

每一步在做什么

  • 组装 → 装上下文：把系统提示、工具定义、记忆、历史和提问拼成一个数组，再数一遍 token 够不够。
  • Thought → Action → 观察：模型先输出一段思考，再输出一个工具调用；外部运行时真正执行工具，把结果塞回消息列表。注意 Thought 和 Action 都是模型生成的文本，执行的不是它。
  • RAG 检索：在「调工具」和「拿到结果」之间，把长文档切块、按相关性召回、重排、截断后注入。
  • 上下文管理 → 循环判定：预算不够就压缩，信息不够就再走一轮。

想深一点

把「压缩策略」设成摘要、预算设成 4k，然后看最后一步：回答还剩下什么？再想想，如果是你自己写这个 Agent，你会先压哪一段？
