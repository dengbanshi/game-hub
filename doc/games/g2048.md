# 2048

按方向键滑动方块，相同数字合并。这个仓库里它是热身，但它对应一个很硬的概念：**状态空间搜索**。

- 分类：`game`
- 入口：`games/g2048/index.html`
- 帮助内容：游戏页内「? 玩法与原理」

---

## 1. 背后的机制

2048 的每一步，都发生在同一个循环里：

```
观察当前状态 → 枚举 4 个合法动作 → 推演每个动作的后果 → 选一个 → 状态转移
```

这就是搜索算法的骨架。真正让 2048 值得玩的地方在于：**状态空间大到不可能穷举**（合法局面约 10¹⁴ 量级），所以你必须依赖启发式——一个「不看完整棵树也能大致判断好坏」的评估函数。

人类玩家用的启发式通常是这几条：

- 把最大数固定在一个角落；
- 保持数字按大小单调排列（一行里从左到右递减）；
- 尽量少动「蛇形」路径的末端。

这三条没有一条是规则要求的，全是经验总结出来的剪枝策略。**推理也是同一回事**：你没有算完所有可能，你只是用一套好的先验砍掉了大部分分支。

## 2. 能学到什么

- **你会看到局部最优不等于全局最优。** 右下角堆大数看起来很稳，但大数一旦被挤到棋盘中间，基本救不回来。
- **你会亲手摸到贪心策略的上限。** 只盯着「这一步能合并多少分」，通常在 512 就崩盘。因为合并不是免费的：它会让棋盘变得不整齐。
- **你会理解「可合并自由度」这个词。** 输的原因几乎从不是「数字不够大」，而是某一列被小数字冻结，四个方向都无法产生变化。
- **你能体会启发式的价值。** 同一个人、同一个棋盘，用「只往左上滑」这条约束，分数能翻好几倍。约束不是限制，是剪枝。

## 3. 玩法规则

1. 方向键或 WASD 移动，手机上直接滑动棋盘。
2. 所有方块朝同一方向滑动，相邻且数字相同的两块合并成一块，数值相加。
3. 每次有效移动后，空格里随机出现一个 2（90%）或 4（10%）。
4. 棋盘填满且四个方向都无法合并时，本局结束。
5. 合并时得分等于合并后的数值（两个 64 合并得 128 分），最高分存在本浏览器。

## 4. 代码设计

两个文件：`index.html`（结构 + 样式 + 帮助内容）与 `game.js`（规则、渲染、复盘，约 330 行）。

拆出来的直接原因是加了复盘之后逻辑超过了 200 行；更重要的原因是**复盘里的机械策略必须和界面共用同一份棋盘规则**，否则对照出来的数字来自另一套规则，等于没对照。所以棋盘操作全部下沉成纯函数（`applyMove` / `canMove` / `maxTile` / `maxInCorner`），界面和策略模拟都调它们。

核心是这几个函数：

```js
// 把一维行的合并逻辑写一次，四个方向全部复用
function slideLine(line) {
  const values = line.filter((v) => v !== 0);   // 先去掉空格，滑动方向就统一了
  const out = [];
  for (let i = 0; i < values.length; i++) {
    if (values[i] === values[i + 1]) {
      out.push(values[i] * 2);                   // 合并
      i++;                                       // 跳过被吃掉的下一块
    } else out.push(values[i]);
  }
  while (out.length < N) out.push(0);
  return { out, gained };
}
```

四个方向不写四套合并逻辑，而是用 `readLine` / `writeLine` 把任意方向**转成「从左往右」**再处理：

- 左：直接取
- 右：取反
- 上：取列
- 下：取列后取反

这是典型的「把 N 种情况归约成 1 种」——`slideLine` 只需要正确一次，四个方向的正确性由中间那层保证。

### 已知取舍

- **没有 undo。** 有 undo 就变成搜索引擎而不是游戏了，玩家会开始暴力试错，正好绕开了「要为自己的一步负责」这件事。
- **随机数从 `Math.random()` 改成了种子 PRNG（`mulberry32`）。** 上一版这里是规范里的例外，理由是「2048 的失败归因在棋盘形状，不在随机数」。加复盘之后这个理由不成立了：反事实要拿**同一个开局**让另一种策略重跑，没有可复现的随机流就没有对照。现在每局的种子存在状态里，也显示在面板右上角，可以拿去复算。
- **机械策略永远不按「上」。** 这是它的定义，不是遗漏。它因此会在「只剩上能走」的局面下提前结束——这也算在它的成绩里，不是网开一面。
- **它不直接讲推理机制。** 它讲的是搜索结构的直觉。真正对口的推理游戏是 `speculative`（投机采样）和 `context-window`（上下文窗口）。

## 5. 复盘面板

由 `shared/review-panel.js` 渲染，本游戏只提供数据。

| 段 | 内容 |
| --- | --- |
| 判定 | 按最大块分四档：`≥2048` / `≥1024` / `≥512` / 其余，各配一句诊断 |
| 指标 | 最终分数、最大块、有效移动次数、无效按键次数 |
| 归因 | 三条：最大块待在角落的步数占比、无效按键占比、「第 N 步之后最大块离开角落再没回去」 |
| 反事实 | 同一个种子（同开局），换成「只按下→左→右、永不按上」的机械策略重跑；外加 10 个开局的中位分 |
| 建议 | 一条：角落驻留 / 无效按键 / 机械策略谁更强，挑最突出的那个信号 |

**反事实为什么用机械策略，而不是「理论上限」**：理论上限算不出来，也算不上可验证；机械策略是同一套合并规则、同一个开局跑出来的，玩家可以自己复算。实测同一开局下它常拿到 2000~4000 分，而多数人第一次玩停在 500~800——差距不在反应速度，在于它从不为了一次合并牺牲角落。

**「最大块离开角落」怎么算**：每一步合并后记一次 `maxInCorner()`，取最后一次为真的下标 +1。若最后一步仍在角落，这一条改成正面反馈（否则会在一局好棋上报「你输在 X」，那是最伤信任的错误）。
