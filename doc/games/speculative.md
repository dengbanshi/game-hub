# 投机采样 · 猜词接力

让你亲手决定「每轮让 draft 猜几个」，然后看着加速比在某个 k 之后掉头。

- 分类：`inference`
- 入口：`games/speculative/index.html`
- 帮助内容：游戏页内「? 玩法与原理」

---

## 1. 背后的机制

### 问题：解码是串行的，而 GPU 讨厌串行

自回归生成每吐一个 token，都要把整个模型跑一遍前向。单次前向里，显卡的大部分时间在等显存把权重搬进计算单元——算力利用率常常只有个位数。你想提高吞吐，直觉是加大 batch，但 batch 加大只提升吞吐，不降低单条请求的延迟：**第 100 个 token 必须等第 99 个算完**。

这是投机采样要解决的困境：解码的串行依赖没法从算法上消除，但可以让每一次串行步骤多产出几个 token。

### 做法：先猜，再批量验收

1. 一个便宜的小模型（draft）连续猜 k 个 token。它是自回归的，但很小，快。
2. 大模型（target）做**一次**前向，并行验证这 k+1 个位置的概率。
3. 从左到右逐个判定：这个猜测能不能接受？
4. 遇到第一个不能接受的，就在那里截断，由 target 重新采一个 token 补上，然后进入下一轮。

判定规则是核心，不是「猜对了就接受」这么粗糙：

```
接受概率 = min(1, p_target(x) / p_draft(x))
```

取一个 0 到 1 的随机数 u，`u < 接受概率` 就接受。直觉上：如果 target 觉得这个词的概率不低于 draft，无条件接受；如果 target 觉得明显更低，就按比例打折。

### 为什么它是精确的

这是最容易讲错的地方。被拒之后不是丢弃重来，而是从**残差分布**里重新采样：

```
p_residual ∝ max(0, p_target − p_draft)
```

这样采样出来的 token，其边际分布恰好等于 target 单独解码的分布。所以投机采样是**无损加速**：输出分布一模一样，只是更快。

这一点值得单独记住，因为它区分了两类完全不同的做法：

| 做法 | 输出质量 | 加速来源 |
| --- | --- | --- |
| 用小模型直接生成 | 有损，分布偏移 | 换了个更小的模型 |
| 投机采样 | 无损，分布一致 | 用多余的算力换串行步数 |

### 为什么 k 不能无限大

每一轮的成本是验证 k+1 个位置，收益是「连续接受的长度 + 1」。第 j 个位置被接受的前提是前 j−1 个都被接受，所以期望收益是按位相乘的：

```
期望推进 = 1 + α₀ + α₀α₁ + α₀α₁α₂ + …
```

α 是单步接受率。k 每加一位，新增的收益是前面所有 α 的连乘——它在指数衰减。而成本是线性（甚至超线性）增长的。两条线必有一个交点，交点之后就是纯亏。

真实系统里还有一个额外的衰减源：draft 是在**自己猜出来的历史**上继续猜的。j 越大，它的上下文越偏离 target 会走的路，单步接受率本身就在下降。这就是本项目里 `gamma` 参数要建模的东西。

## 2. 能学到什么

- **你会看到 k 不是越大越好。** 第一反应都是「猜长一点更快」，三档难度各跑一遍，你会看到最优 k 分别是 8 / 4 / 2。偏差越大，长串越亏。
- **你会看到接受率是按位相乘的。** 每轮的验收轨道把每一步的 `p_draft / p_target / 接受概率 / u` 都摊开，你能指着某一行说「就是这里比值 0.61 小于 u 0.72，被拒的」。
- **你会看到拒绝的代价是时间，不是质量。** 被拒之后那一格由 target 从残差重采样，出来的仍然是正确的词。整句读完你会发现句子完全正确——投机采样不改输出，只改耗时。
- **你会看到 k 过大的极端后果。** 在「偏差大」档选 k=16，加速比会掉到 0.89×，也就是比老老实实逐 token 生成还慢 11%。这不是惩罚设计，是真实会发生的事。
- **你会理解为什么线上要动态调 k。** 固定 k=4 在「接近」档只有 2.85×，而 k=8 能到 3.08×；同一套系统换个模型对，最优值就变了。

## 3. 玩法规则

### 操作

1. 选难度：**接近 / 中等 / 偏差大**，决定 draft 与 target 的分布差距。
2. 选 **k**：1 / 2 / 4 / 8 / 16。
3. 点「验证一轮」，看 draft 猜出的 k 个 token 被逐个验收。
4. 重复，直到整句 39 个 token 生成完毕。

### 判定细节

每一轮的实际过程：

1. draft 按自己的分布连猜 k 个 token（不足句尾时按剩余长度）。
2. target 对每个猜测给出 `p_target`，计算 `接受概率 = min(1, p_target / p_draft)`。
3. 与固定的随机数 `u` 比较，`u < 接受概率` 则接受，继续看下一个。
4. 遇到第一个拒绝：截断，从残差分布重采样一个 token 补位，本轮结束。
5. 全部接受：额外赠送 1 个 token（target 那次前向顺带给出了下一个位置的概率）。
6. 无论中途是否被拒，**本轮成本都按 k 计**——验证是一次前向并行算完的，钱已经花了。

被拒之后的那几个猜测会以灰色显示「已截断，未验证」：成本付了，收益为零。这就是长 k 的真实代价。

### 计分

```
基线耗时 = 39（逐 token 生成，每个 token 1 个单位）
本轮耗时 = 1 + 0.05k + 0.004k²
加速比   = 39 ÷ 累计耗时
```

- 线性项对应「并行验证 k+1 个位置」的边际开销。
- 平方项对应长序列下 attention 的二次复杂度和 kernel 效率下降。
- 加速比 < 1 表示比基线还慢。

### 固定随机数

同一个位置、同一档难度下，draft 抽到的 token 和验收用的 u 每次都一样（种子 `20261120`）。所以「换个 k 再跑」是**受控对照实验**，不是重开一局碰运气。复盘里的 k 曲线也基于同一套随机数，可以直接和你的实际成绩比。

## 4. 代码设计

### 文件划分

| 文件 | 职责 |
| --- | --- |
| `index.html` | 结构 + 帮助内容（`#gh-help-source`） |
| `game.css` | 专有样式，自有变量用 `--sp-*` 前缀 |
| `game.js` | 概率模型、单轮规划、渲染；复盘只负责算数，排版交给 `shared/review-panel.js` |

### 核心数据结构

```js
// 一条猜测的完整证据链
{
  pos: 12,        // 绝对位置
  j: 2,           // 本轮内第几个（决定 draft 的衰减程度）
  token: '的',
  pd: 0.522,      // p_draft
  pt: 0.860,      // p_target
  ratio: 1.000,   // min(1, pt/pd)
  u: 0.995,       // 固定的验收随机数
  ok: true,
}
```

### 唯一算法入口

`planRound(pos, k, levelId)` 返回一轮的全部结果。游戏内的动画和复盘里的 k 曲线**都调用它**。

这不是为了少写代码，是为了避免两份判定逻辑慢慢跑偏——教学游戏里最尴尬的情况，就是游戏内算一套、复盘报另一套。

```js
// 先生成全部猜测（draft 确实是先猜完再验证的），再从左往右判
for (let j = 0; j < slots; j++) {
  const draft = draftDist(pos + j, j, level);
  const token = sample(draft.order, draft.dist, rand01(pos + j, 1));
  const target = targetDist(pos + j);
  const pd = draft.dist[token];
  const pt = target.dist[token] || 0;
  guesses.push({ pd, pt, token, ratio: Math.min(1, pt / pd), u: rand01(pos + j, 2) });
}
```

### 概率模型

每个位置三个候选：正确答案 + 两个干扰词。

```
p_target = { gold: pt, decoy1: (1−pt)/2, decoy2: (1−pt)/2 }
p_draft  = { gold: pt × weak × gamma^j, decoy1: ·/2, decoy2: ·/2 }
```

- `pt` 由词性决定：标点 0.94，虚词 0.86，实词 0.72。
- `weak`：draft 的基础把握弱化比例。
- `gamma^j`：draft 沿着自己猜出的历史走，误差随位置累积。

这个构造有个好性质：单步接受率的期望恰好是

```
α = dg + (1 − pt)
```

其中 `dg = pt × weak × gamma^j`。前半是「draft 猜对了正确答案」，后半是 min(1,·) 规则白送的部分（draft 选了 target 更喜欢的词时无条件接受）。参数一改，α 立刻可以手算验证——这也是 `gamma` 从 0.80 调到 0.65 的依据：原参数下「偏差大」档的最优 k 落在 4，和真实经验不符。

### 三档参数与实测结果

| 难度 | weak | gamma | k=1 | k=2 | k=4 | k=8 | k=16 | 最优 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 接近 | 0.86 | 0.97 | 1.68 | 2.19 | 2.85 | **3.08** | 2.01 | k=8 |
| 中等 | 0.75 | 0.90 | 1.61 | 2.06 | **2.40** | 2.06 | 1.33 | k=4 |
| 偏差大 | 0.55 | 0.65 | 1.54 | **1.75** | 1.73 | 1.35 | 0.89 | k=2 |

（表内为加速比，由 `simulate()` 用固定种子跑完整句得到，可复现。）

三档的最优 k 构成 8 → 4 → 2 的梯度，偏差大到一定程度时 k=16 直接跌破 1。这就是这个游戏要传达的那条曲线。

### 确定性随机

```js
function rand01(pos, channel) {
  let x = (pos * 374761393 + channel * 668265263 + SEED) >>> 0;
  x = Math.imul(x ^ (x >>> 13), 1274126177) >>> 0;
  return ((x ^ (x >>> 16)) >>> 0) / 4294967296;
}
```

通道区分用途：1 = draft 采样，2 = 验收，3 = 残差重采样。

不用 `Math.random()` 的理由是可解释性：如果每次重开都换一组随机数，玩家看到加速比变化时无法判断「是我选错了 k，还是运气变了」。固定随机数之后，同一档难度下不同 k 的差距**纯粹来自策略**。

### 已知取舍

- **词表只有 3 个候选。** 真实的词表是 5 万级，残差分布会分散到很多词上。这里压到 3 个是为了让屏幕上的概率能看清楚，代价是残差重采样几乎总是落在正确答案上。想要更真实，把 `decoysFor` 改成返回 5~8 个候选即可，判定逻辑不用动。
- **耗时模型是手调的。** 真实 GPU 上 k=4 常常能拿到 2.5~3×，因为验证 k+1 个 token 的墙钟时间接近 1 次前向。这里用了偏保守的 `1 + 0.05k + 0.004k²`，目的是让「k 过大」的代价在几十秒内可见。**不要把这个公式当成性能模型**。
- **没有模拟 batch。** 真实的投机采样要和连续批处理、KV Cache 共享一起看，单条请求的加速比和系统吞吐是两回事。
- **gamma 是全局常数。** 真实中衰减取决于文本难度：代码里的长串比自然语言更稳定。

## 5. 复盘面板

39 个 token 全部生成后由 `shared/review-panel.js` 渲染，本游戏只提供数据。

| 段 | 内容 |
| --- | --- |
| 判定 | 按加速比分四档：`<1`（比基线还慢）/ `<1.5` / `<2.2` / `≥2.2`，各配一句诊断 |
| 指标 | 最终加速比、总耗时、接受率（接受数 ÷ 猜的总位数）、平均接受长度 |
| 归因 | 逐轮表格（轮次 / k / 接受 / 推进 / 本轮耗时 / 累计加速比），附一句「最亏的是第 N 轮」 |
| 反事实 | 同一难度、同一种子，把 k=1/2/4/8/16 各跑一遍整句，条形对照，标出「你这局」与「最优」 |
| 建议 | 一条：本档最优 k、曲线为什么在最优之后掉头，附本档历史最好成绩 |

**反事实为什么可信**：`simulate(k, levelId)` 和游戏内用的是同一个 `planRound()`，随机数由 `位置 + 通道 + 种子` 派生。所以同一档难度下换 k，差异**只来自 k 本身**，不是运气。这一条是这个游戏能成立的前提，也是它区别于「点着玩的动画」的地方。

**「最亏的一轮」怎么算**：取 `advance / slots` 最小的一轮（只统计 k>1 的轮次）。它回答的是「哪一轮的钱白花了」，不是「哪一轮最慢」——这两件事经常不是同一轮，因为耗时只和 k 有关，而收益和接受率有关。
