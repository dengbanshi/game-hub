# 上下文窗口 · 记忆背包

24 格预算，4 轮信息流，你决定每条留原话、压成摘要，还是直接扔掉。最后用留在窗口里的东西回答问题。

- 分类：`agent`
- 入口：`games/context-window/index.html`
- 帮助内容：游戏页内「? 玩法与原理」

---

## 1. 背后的机制

### 窗口是硬约束，而且比你想的更硬

上下文窗口有明确上限，超了就报错或被截断。但真正麻烦的不是上限，是**注意力分布不均**：放在长上下文中间的信息，被用到的概率明显低于开头和结尾。这不是玄学，是长序列注意力机制的固有性质——位置越远、竞争项越多，单个片段的权重就越低。

于是「把全部历史都塞进 prompt」这件事，在两个层面上都不成立：

1. 物理层面：装不下。
2. 效果层面：装下了也未必被看见。冗余信息会稀释关键信息的权重。

### 三种操作，对应三种真实手段

面对不断堆积的历史，你能做的事情只有三类：

| 操作 | 真实系统里叫什么 | 代价 |
| --- | --- | --- |
| 保留原文 | raw message / 原始工具返回 | 占格最多，信息最完整 |
| 压缩 | summarization / extraction | 省格，但**有损**，细节和数字会消失 |
| 丢弃 | eviction / truncation | 不占格，彻底不可恢复 |

关键在第二行那句「有损」。摘要能留住「有一笔变更」，但留不住「新增了优惠券校验，涉及 coupon-svc」。而排障恰恰是**数字和名词决定结论**的场景：知道「有个下游超时」和知道「超时阈值 500ms、实际耗时 620ms」，能得出的结论完全不同。

这就是这个游戏的核心张力：压缩在做的当下永远划算，代价要到提问时才结算。

### 为什么全记住反而更差

这是本游戏想让你亲手撞上一次的反直觉点。预算固定时，留下的每一格闲聊都等于从证据里扣掉一格。看似「多记一点没坏处」，实际上：

- 预算被挤占 → 关键证据进不来；
- 就算都塞进去了，噪音会拉低关键信息在注意力里的相对权重。

真实 Agent 的解法不是「更大的窗口」，而是**外部记忆 + 按需检索**：把历史写进外部存储，需要时再捞回来。窗口应该装「当前这一步需要的东西」，而不是「所有发生过的事」。

## 2. 能学到什么

- **你会看到占位最大的信息往往最没用。** 一顿午饭的讨论占 8 格，一段能定根因的日志占 6 格。按「占得多就重要」来留，第一轮就输了。
- **你会亲手体会压缩的代价是延迟结算的。** 压缩的那一刻省下格子很爽，等到问「超时阈值是多少」时才发现数字没了。这个时间差，就是真实系统里上下文管理最难的地方。
- **你会看到噪音挤掉证据的具体过程。** 第 3 轮那条 6 格的日志进不来，通常不是因为它不重要，而是因为前面留了 8 格午饭。
- **你会理解「答对」和「有据可依」的区别。** 凭常识蒙对和用证据推出来，在复盘里是两种不同的颜色——真实事故里这两种情况的下场也完全不同。
- **你会自己发现那条中间线。** 全留原文会被预算卡死，全压缩会被细节缺失卡死。能拿满分的策略只有一个形状：**关键证据留原文，次要信息压缩，闲聊不留**。

## 3. 玩法规则

### 基本设定

- 上下文预算 **24 格**。
- 信息分 **4 轮**进来，每轮 2~3 条，共 11 条。
- 过程中和结尾共 **3 道题**。

### 每条信息的三种处理

| 操作 | 占用 | 后果 |
| --- | --- | --- |
| 保留原文 | `size` 格 | 保留全部细节 |
| 压缩 | `⌈size / 3⌉` 格 | 只剩「有这件事」，数字与细节丢失 |
| 丢弃 | 0 格 | 不可恢复 |

- 只占 1 格的条目不能再压缩（压了还是 1 格，纯亏）。
- 预算不足时无法加入新内容，会提示还差几格，必须先压缩或移除已有条目。
- 窗口里的条目随时可以再压缩或移除——真实系统里也是这样，空间不够时回头整理。

### 提问与判定

每题三个选项，判定分三档：

| 情况 | 得分 | 标记 |
| --- | --- | --- |
| 选对，且所需证据都在窗口里（该留原文的留了原文） | 20 | 有据可依 |
| 选对，但证据缺失或被压缩到没有细节 | 10 | 蒙对了 |
| 选错 | 0 | 答错 |

满分 60。

「所需证据」由题目声明。例如「超时阈值设成了多少」要求 `c2`（日志）**保留原文**——压缩后的摘要里没有 500ms 这个数。

### 复盘指标

| 指标 | 含义 |
| --- | --- |
| 预算峰值占用 | 过程中最高用到多少格，衡量你的窗口有多臃肿 |
| 噪音占窗口 | 最终留在窗口里的无关内容比例 |
| 关键证据丢失 | 被丢弃的关键条目数量 |

分数相同、指标不同，说明策略不同：有人靠压缩挤出空间，有人靠丢弃硬扛。指标会告诉你是哪一种。

## 4. 代码设计

### 文件划分

| 文件 | 职责 |
| --- | --- |
| `index.html` | 结构 + 帮助内容 |
| `game.css` | 专有样式（`--cw-*` 前缀） |
| `scenario.js` | **纯数据**：场景、11 条信息、3 道题 |
| `game.js` | 预算核算、决策、判分、复盘 |

`scenario.js` 里没有任何 DOM 操作和副作用，换场景只改这一个文件。这是 `ARCHITECTURE.md` §4.2 对数据文件的硬要求。

### 数据结构

```js
// 一条信息
{ id: 'c2', from: '日志', title: '超时 32417 次',
  detail: 'CouponService.query timeout after 500ms …',
  size: 6, value: 'key' }     // key | weak | noise
```

`value` 不参与实时判定，只用于复盘统计。玩家在玩的时候看不到它——这是刻意的，否则就等于给了答案。

### 事件队列

轮次和提问混在一起，如果散在渲染逻辑里写 `if`，很快就会变成一团。这里先把它们排成一个队列：

```js
SCENARIO.rounds.forEach((round) => {
  queue.push({ type: 'round', round });
  SCENARIO.questions
    .filter((q) => q.afterRound === round.id)
    .forEach((q) => queue.push({ type: 'question', question: q }));
});
```

之后整个流程就是 `cursor` 往前走一格，`loadStage()` 按 `type` 分派。加一轮信息、加一道题都不用改流程代码。

### 预算核算

`decide()` 是唯一修改窗口的入口，所有加法都经过它：

```js
const baseUsed = usedSlots() - (existing ? existing.slots : 0);
if (mode !== 'drop' && baseUsed + nextSlots > SCENARIO.budget) {
  // 提示还差几格，拒绝这次操作
  return;
}
```

先减掉旧占位再判断，是因为「原文→压缩」这种降级操作必须能通过预算检查——否则玩家会陷入「想压缩但被拒绝」的死锁。

### 判分

```js
function evaluate(question, choice) {
  const correct = choice === question.answer;
  const missing = question.needs.filter((need) => {
    const entry = state.window.find((e) => e.item.id === need.item);
    if (!entry) return true;                                    // 没留
    return need.level === 'full' && entry.mode !== 'full';       // 只留了摘要
  });
  if (!correct) return { credit: 0, correct: false, missing };
  if (missing.length) return { credit: 10, correct: true, missing };
  return { credit: 20, correct: true, missing: [] };
}
```

返回 `missing` 而不是只返回分数，是为了让复盘能说清「你这 10 分缺的是哪一条原文」——不能归因的扣分等于没扣。

### 已知取舍

- **只有 11 条信息、24 格。** 真实上下文是几十万 token、上百条历史。这里压到能在一屏内看完，代价是没有体现「信息量大到必须批量处理」的压力。想加大难度，改 `scenario.js` 的 `budget` 和条目即可，逻辑不用动。
- **「压缩」被简化成丢弃 detail。** 真实摘要会有损但不会损到一点不剩，而且摘要质量本身是个模型能力问题。这里用「摘要一律丢细节」来保证规则可预测——否则玩家无法判断某次压缩到底剩下了什么，失败就不可归因了。
- **没有模拟 lost-in-the-middle。** 真实系统里同样两条证据，放在窗口开头和中间的效果不一样。这里所有条目权重相同。要模拟的话，得给每条加一个「位置衰减」，但那会让判定规则复杂到玩家无法预测，得不偿失。
- **噪音是人为标注的。** 真实世界里没有 `value: 'noise'` 这个字段，判断一条信息是否相关本身就是最难的部分。游戏把这一步替你做了，只考「预算分配」这一层。
