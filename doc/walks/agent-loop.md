# Agent 经典循环

一句话：用一个具体提问走完一整轮 Agent 循环，看清上下文是被什么撑爆的、压错了会丢掉什么。

- 形态：`walk`
- 分类：`agent`
- 入口：`walks/agent-loop/index.html`
- 步骤：13 步
- 在线：https://dengbanshi.github.io/game-hub/ （大厅里点开）

## 1. 这条链路在讲什么

Agent 不是「更聪明的模型」，是**一个带循环的提示词**。模型本身还是那个一次前向出一段文本的东西；循环、工具、检索、上下文管理都在外面那层代码里。

这句话说起来简单，但它带来一个反直觉的结论：**Agent 答得不好，绝大多数时候不是模型不行，是那一步该有的信息没到位。** 所以这个图解不讲模型，只讲信息怎么流动——从组装提示词开始，到最终回答为止，每一步都在回答「此刻上下文里有什么、少了什么」。

全程用同一个具体问题走完：

> 上周三例会上定的数据库方案是什么？为什么没选另一个？

挑这个问题是因为它天然需要三次不同动作：先确定「上周三」是哪天（要调日历），再翻会议纪要（要检索），最后找到「为什么没选另一个」的对比段落（要第二轮检索）。一次前向解决不了，才值得看循环。

## 2. 能看出什么

- **一句话提问的真实成本**：系统提示 620 + 工具定义 1140 + 记忆 900 + 历史 1600 + 提问 32 = 4292 个 token。用户写的那句话占 **0.7%**。工具定义是固定开销，每加一个 MCP 工具它都会变长，而且对每一句话都要重复发一遍。
- **上下文是被工具返回撑爆的，不是被对话撑爆的**：一次日历查询带回 480 token，两段文档节选带回 1180 + 2340 token。几处工具返回加起来占了整个上下文的一半以上，而真正进到最终回答里的只有几十个字。
- **压缩策略没有通用最优**：默认的「压成摘要」恰好抹掉了「为什么没选另一个」那半句——因为摘要天然丢细节，而细节往往正是你问的东西。换成「丢最旧的历史」反而更好，因为那段历史本来就跟本问无关，但这个结论**换个问题就反过来了**。
- **关掉检索，答案不会变空，会变错**：模型不会说「我查不到」，它会编一个方案名，理由还是真的（从别处拼来的）。这比空着危险得多。
- **循环有三个退出条件**：模型觉得够了 / 轮数到顶 / 预算耗尽。只有第一个是「任务完成」，另外两个都是异常出口——而且它们**不报错**，会带着半截信息给出一个看起来完全正常的回答。

| 2 | 组装提示词 | 五部分各占多少 token，固定开销有多大 | — |

| 8 | Thought ② | 模型判断「还缺对比理由」 | — |

参数表：

| 参数 | 类型 | 范围 | 影响哪几步 | 为什么放在这里 |
| --- | --- | --- | --- | --- |
| 上下文预算 | 滑块 | 4k~32k | 3, 11, 13 | 它决定「会不会触发压缩」，是最上游的开关 |
| 启用 RAG | 开关 | 开 / 关 | 7, 8, 13 | 关掉之后整条链路的结论性质会变（从「查不到」变成「编」） |
| 召回段数 | 滑块 | 1~5 | 7, 10, 11, 13 | 多召回一段多 780 token，同时多一份噪声 |
| 最大轮数 | 滑块 | 1~6 | 12, 13 | 本问需要 3 轮，调到 2 就会被掐断 |
| 压缩策略 | 单选 | 压成摘要 / 丢最旧的历史 / 不处理 | 11, 13 | 三种策略在这一个问题上结论完全不同 |

## 4. 代码设计

三个文件，`walk.js` 约 600 行：

```
walks/agent-loop/
├── index.html   骨架 + 帮助内容
├── walk.css     只放本图解独有的画法（气泡 / 思考块 / 代码块 / 召回卡）
└── walk.js      数据 → 纯函数 → 三个判定函数 → steps → mount
```

核心是一个**唯一的 token 口径**。这是第一版踩过的坑：三个步骤各写了一次硬编码总数，把 `召回段数` 拖大之后，三屏显示的是三个互相矛盾的累计值。

```js
// 循环内的追加顺序，必须和步骤顺序完全一致。
// 所有步骤都只问「到这里为止累计多少」，不许自己手写加法。
const FLOW_COST = [
  { key: 'thought1', tokens: () => COST.thought1 },
  { key: 'action1', tokens: () => COST.action1 },
  { key: 'obs1', tokens: () => COST.obs1 },
  { key: 'rag', tokens: (v) => (v.rag ? Number(v.ragTopK) * COST.chunk : 0) },
  { key: 'thought2', tokens: () => COST.thought2 },
  { key: 'action2', tokens: () => COST.action2 },
  { key: 'obs2', tokens: () => COST.obs2 },
];

function cumulative(values, upToKey) {
  let sum = BASE_TOKENS;
  for (let i = 0; i < FLOW_COST.length; i += 1) {
    sum += FLOW_COST[i].tokens(values);
    if (FLOW_COST[i].key === upToKey) break;
  }
  return sum;
}
```

另外两个函数把「压缩」和「回答」的因果关系固定下来，第 11、12、13 步共用同一份判断，不会各说各的：

- `compressOf(values)` → `{ used, budget, over, after, detailLost, verdict }`
- `answerOf(values)` → `{ hasConclusion, hasReason }`

`answerOf` 里把「结论」和「理由」拆成两个独立布尔值，是因为它们缺的原因完全不同：

| 缺什么 | 触发条件 | 读者看到的回答 |
| --- | --- | --- |
| 结论错 | `rag` 关闭 或 `maxTurns < 2` | 一个编造出来的方案名 + 一个真理由 |
| 理由缺 | `rag` 开但 `turns < 3`，或压缩抹掉了细节 | 正确结论 + 缺失的第二问 |

### 哪些数字是真算的，哪些是示意的

| 数字 | 来源 | 真实 / 示意 |
| --- | --- | --- |
| 基础材料 4292 token（620/1140/900/1600/32） | 按 7B 级模型的实际量级估 | **半真实**：量级可信，具体到个位是估的 |
| 每次工具返回 480 / 1180 token | 按真实 JSON / 文档节选的体量估 | **半真实** |
| 上下文累计、超出量、压缩后大小 | 由 `cumulative` / `compressOf` 实算 | 真实（算式真实，输入是估的） |
| 日历返回、文档节选、召回的 5 段文字 | 编的具体内容 | **示意** |
| 循环判定「本问需要 3 轮」 | 人为设定 | **示意** |

这张表里必须诚实的是：**算式是真的，输入是估的**。所以对外只讲结论性的比较（「摘要会抹掉细节」「关掉检索会变编」），不讲「所以你该把预算设成 9216」——后者依赖那些估算不成立。

### 已知取舍

- 只有一个场景。多场景能覆盖更多分支，但读者会失去「同一件事走到黑」的连贯感，而连贯感是这个图解唯一比文字强的地方。
- 工具调用写的是简化 JSON，不是真实 function-call 格式。真实格式因厂商而异，写进来只会增加噪音。
- 轮数固定为 3（thought → action × 2 → 判断）。真实 Agent 的轮数是不确定的，这里把不确定性让给「最大轮数」这个参数来表达。
- 压缩效果是**规则算的**，不是真的调模型摘要。真实摘要质量和丢什么，比这里复杂得多；图解只能保证「摘要会丢细节」这个方向是对的。
