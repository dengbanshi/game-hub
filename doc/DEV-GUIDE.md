# 开发规范

> 配套文档：[ARCHITECTURE.md](./ARCHITECTURE.md)（结构与契约）。本文只讲**怎么做**，不讲为什么分层。
> 违反下面任一「硬规则」，改动不应该合并到 `main`。
>
> 仓库有两种产物：**游戏**（有输赢，带复盘）和**图解**（无输赢，带步骤导航）。下面的规则里，
> 凡是写「条目」的地方两者都适用；只适用其一的会写明「游戏」「图解」。

---

## 1. 五条硬规则

### 规则一：每个条目都必须有一份配套文档

路径固定 `doc/games/<id>.md` 或 `doc/walks/<id>.md`，结构与 `kind` 对应，见 [§2](#2-条目文档模板)。

**为什么**：这个仓库的产出是「理解」，不是「代码」。没有文档的条目，半年后连作者自己都说不清它到底想讲什么，读者更不可能知道该盯着哪里看。

**怎么检查**：`games.json` 里每条的 `doc` 字段指向的文件必须存在，且段数与 `kind` 匹配（游戏五段，图解四段）。

### 规则二：每个条目必须有帮助入口

不允许自己做，必须用共享层：页面里放 `<header id="gh-bar" data-title="…">` 和 `<div id="gh-help-source" hidden>`，脚本引入 `shared/game-shell.js`。按钮由共享层注入。

**为什么**：帮助内容是"这个条目在讲什么"的唯一现场入口。读者不会去翻仓库文档——他是在玩 / 翻页的时候产生疑问的。做成统一注入，才能保证不会因为"这次赶时间"而漏掉。

**怎么检查**：打开条目 → 右上角出现「? 玩法与原理」→ 点击有内容。缺失时控制台会 `console.warn`。

图解页的按钮文字是一样的「? 玩法与原理」。不要为图解改成「? 说明」——读者不会去分辨两种形态，同一个位置同一个词反而更好找。

### 规则三：游戏必须有复盘；图解不许有分数

不允许自己写复盘的 HTML 和 CSS，必须调共享层：

```js
GameReview.show({ meta, verdict, metrics, attribution, counterfactual, advice });
GameReview.hide();   // 重开局时
```

面板固定五段（判定 / 指标 / 归因 / 反事实 / 建议），其中 `verdict`、`counterfactual`、`advice` 是必填。缺了会在**页面上**出现红色告警，不只是控制台。

**为什么**：只给分数，玩家带走的是手感；给出「你为了 X 牺牲了 Y」和「换个做法会怎样」，带走的才是理解。五段里真正起作用的是第 ④ 段**反事实**——前四段只是把分数换个说法，只有对照能让玩家自己得出结论：「原来最优是 k=2，我多猜了 8 倍反而更慢。」

**反事实的硬性要求**：必须可复现。同一套规则、同一个种子或同一个初始局面，只改一个变量。做不到复现的「理论上限」不要写——玩家没有理由相信一个算不出来的数字。

**怎么检查**：打完一局 → 面板出现 → 数到四段（指标 / 归因 / 反事实 / 建议）都在 → 反事实里至少两条对照，且有一条标了「你这局」。

#### 图解不适用复盘，但有三条红线

复盘的前提是「有你这局」——有决策、有后果、有「换个做法会更好」。图解没有输赢，硬加复盘只会变成一句空话（"你浏览了 12 步"）。所以：

- **不要**引入 `shared/review-panel.js` / `review-panel.css`，误引入时控制台会告警。
- **不要**给图解加分数、评级、通关、成就。

图解存在的意义是把「过程」讲清楚，一旦有了分数，读者就会去优化分数而不是理解机制，而且没人说得清那个分数是怎么算的。

替代复盘的是这三条，写进 [§7 自查清单](#7-提交前自查清单)：

| 红线 | 反例 | 为什么不行 |
| --- | --- | --- |
| **步骤可逆**：每一步都能从任意方向到达（上一步 / 点流程图 / 键盘 ← →），不能是单向播片 | 只有「下一步」，走到头就没了 | 图解的价值在对照。读者一定会往回翻，「刚才那步是什么来着」是最常见的动作 |
| **参数真实联动**：拧了参数，当前这一屏必须真的变 | 滑块只更新旁边那个数字，画面不动 | 拧了没反应，读者会认定整页都是插画，后面所有数字都不再可信 |
| **数字要能对上**：同一份数据在多个步骤出现时，必须由同一个函数算出来 | 第 9 步写 `8972 token`，第 11 步写 `9000 token` | 图解里最容易出的错。读者会拿两屏对照，一旦对不上，整篇结论都失效 |

**怎么检查**：翻完所有步骤，每一步非空且无报错；至少 3 个参数各拖一次，画面确实变化；随便挑两个都显示同一指标（比如上下文 token 数）的步骤，数字必须相同。

### 规则四：关键逻辑必须有关键注释，风格必须统一

见 [§4 代码风格](#4-代码风格) 与 [§5 注释](#5-注释)。

**为什么**：这类教学游戏的代码会被"想改个参数试试"的人反复读。注释解释的是**约束和取舍**，不是语法。

### 规则五：必须遵循既有架构，只允许增量扩展

- 允许：新增 `games/<id>/`、新增 `walks/<id>/`、在 `games.json` 加条目、给已有条目加参数 / 步骤、改善单个条目内部实现。
- 不允许（需审核）：改 `shared/` 行为、改 `games.json` 字段结构、改分层与依赖方向、改动 `GameWalk.mount` 的 config 契约、引入第三方依赖或构建步骤。

**为什么**：静态站点没有类型系统兜底，架构漂移不会报错，只会在某天变成"没人敢动"。审核成本远低于返工成本。

**流程**：先改 `ARCHITECTURE.md` 的变更记录 → 说明动机与影响面 → 维护者确认 → 全量回归所有条目（游戏要打完一局，图解要翻完所有步骤）。

## 2. 条目文档模板

### 2.1 游戏（五段）

复制下面骨架，把尖括号内容换掉。**五段顺序不许改**——顺序一致才能横向对比不同游戏的教学设计。

```markdown
# <游戏名>

一句话：这个游戏让你亲手做什么。

- 分类：`inference` / `agent` / `game`
- 入口：`games/<id>/index.html`
- 在线：https://dengbanshi.github.io/game-hub/  （大厅里点开）

## 1. 背后的机制

<这个概念在解决什么问题。不用教科书式定义，从一个具体困境讲起。3~6 段。>

## 2. 能学到什么

<3~5 条。每条写成「你会看到 X，因此理解 Y」，不要写成「了解 X」。>

- 你会看到 …
- 你会亲手把 … 调坏，然后明白 …
- 复盘面板里的 … 会告诉你 …

## 3. 玩法规则

<操作方式、判定逻辑、失败条件、计分公式。要让读者不看代码也能算出一局的分数。>

## 4. 代码设计

<文件划分、核心数据结构、关键算法、为什么这么拆。给出 5~20 行的核心代码片段。>

## 5. 复盘面板

<这一局的五段分别给玩家什么信息，尤其要写清反事实那一段是怎么算出来的：
同一个种子/开局、只改哪个变量、对照的基准策略是什么。>

| 段 | 内容 |
| --- | --- |
| 判定 | <一句话结论> |
| 指标 | <四个数字，各自代表什么> |
| 归因 | <指到哪一步> |
| 反事实 | <对照组是什么，怎么保证可复现> |
| 建议 | <那一句动作> |

### 已知取舍

<这个游戏简化了什么真实机制，为什么可以简化。诚实写，别装作完整。>
```

### 2.2 图解（四段）

图解没有复盘段，因为它没有「你这局」。取而代之的是**第 4 段必须交代哪些数字是真算的**——图解里必然有示意的部分，不写清楚，半年后会有人把示意当成实测拿去引用。

```markdown
# <图解名>

一句话：这条链路把哪几件事串起来，读者翻完能说清什么。

- 形态：`walk`
- 分类：`inference` / `agent`
- 入口：`walks/<id>/index.html`
- 步骤：N 步
- 在线：https://dengbanshi.github.io/game-hub/  （大厅里点开）

## 1. 这条链路在讲什么

<它把哪几个环节串成一条线，为什么必须一起看。挑一个具体场景讲，不要写目录。>

## 2. 能看出什么

<3~5 条。每条写成「拧哪个参数 / 走到哪一步，会看到什么变化」，不要写成「了解 X」。>

- 把 X 拖到 Y，你会看到 Z —— 这说明 …
- 走到第 N 步时 …
- 关掉 X，结论会变成 …（而且不是变空，是变错）

## 3. 步骤与参数

| # | 步骤 | 这一屏在算什么 | 相关参数 |
| --- | --- | --- | --- |
| 1 | 提示词 | … | — |

参数表：

| 参数 | 类型 | 范围 | 影响哪几步 | 为什么放在这里 |
| --- | --- | --- | --- | --- |

## 4. 代码设计

<文件划分、数据结构、关键算法。

**必须写清：哪些数字是真算的，哪些是示意图。**

| 数字 | 来源 | 真实/示意 |
| --- | --- | --- |
| 参数量 6.97B | 按 32 层 d=4096 的公式实算 | 真实 |
| 注意力矩阵 | 手工挑的对称表 | 示意 |
```

### 写作要求

| 要 | 不要 |
| --- | --- |
| 具体数字、具体现象 | 「显著提升」「大幅优化」这类空话 |
| 承认简化 | 把玩具模型说成真实系统 |
| 解释反直觉的地方 | 复述一遍规则 |
| 一段一个意思 | 一段塞五个概念 |

## 3. 帮助按钮与帮助内容

### 结构（照抄，不要自创）

```html
<div id="gh-help-source" hidden>
  <h3>这是什么机制</h3>
  <p>…</p>

  <h3>你能学到什么</h3>
  <ul><li>…</li></ul>

  <h3>玩法规则</h3>
  <ol><li>…</li></ol>

  <h3>算分方式</h3>
  <ul><li>…</li></ul>

  <h3>想深一点</h3>
  <p>…</p>
</div>
```

图解页的段落标题不一样（没有「玩法规则」「算分方式」，因为图解既不能玩也不算分）：

```html
<div id="gh-help-source" hidden>
  <h3>这条链路在讲什么</h3>
  <h3>你能看出什么</h3>
  <h3>怎么操作</h3>
  <h3>每一步在算什么</h3>
  <h3>想深一点</h3>
</div>
```

### 内容要求

- **不许带内联样式或 class**，排版由 `shared/game-shell.css` 统一控制。
- **不许超过 1.5 屏**。弹层是"现场答疑"，不是文档搬运；深读请去 `doc/games/<id>.md`。
- **必须与文档一致**。改了规则忘了改帮助，是这个项目最容易犯也最难发现的错误——所以它进了 [§7 自查清单](#7-提交前自查清单)。
- 「想深一点」至少写一个问题，指向这个条目最反直觉的点。这是教学价值最高的部分，不要省。
- 图解的「怎么操作」必须写清键盘可以翻页、参数在哪、参数会不会被记住。读者不会自己发现这三件事。

## 4. 代码风格

### 4.1 JavaScript

```js
// 缩进 2 空格；语句结尾必须有分号；字符串用单引号，插值用模板字符串
const CONFIG = { rounds: 5, budget: 30 };   // 模块级常量：UPPER_SNAKE
const boardEl = document.getElementById('board'); // DOM 引用：名词 + El

function renderStats() { /* 动词开头 */ }
```

**强制约定**：

| 项 | 要求 |
| --- | --- |
| 状态管理 | 单一 `state` 对象，改状态后调用 `render()`。**禁止**到处零散改 DOM |
| 事件绑定 | `addEventListener`。**禁止**内联 `onclick="…"` |
| 插入文本 | `textContent` 或 `createElement`。**禁止**把数据拼进 `innerHTML` |
| 定时器 | 存 id，重开 / 卸载时 `clearInterval`。**禁止**裸 `setInterval` 不清理 |
| 随机 | 必须可复现：用带种子的 PRNG，**禁止**直接用 `Math.random()` 做判定 |
| 弹窗 | 用页面内元素。**禁止** `alert` / `confirm` / `prompt` |
| 复盘 | 游戏调 `GameReview.show(...)`。**禁止**自己拼复盘 DOM，也不要把 `.ghr-*` 样式复制进游戏。图解**不使用** `GameReview` |
| 画布原语 | 图解的指标卡 / 条形图 / 流程块 / 判断条必须用 `GameWalk.ui.*`。**禁止**在自己的 `walk.css` 里重写一套 `.xx-bar` |
| 参数声明 | 图解的参数只能在 `GameWalk.mount` 的 `config.params` 里声明一次，步骤按 id 引用。**禁止**每一步各声明一遍 |
| 全局 | 除共享层挂的 `window.GameShell` / `window.GameReview` / `window.GameWalk`，不新增全局变量 |

**关于随机**：教学游戏里「同一条输入，不同 k 得到不同结果」无法归因。用 `位置 + 种子` 派生的确定性随机，才能说清「你输在第 3 步的比值 0.68 上」。这一条不是洁癖，是可解释性的前提。图解同理：同一组参数每次刷新必须画出同一屏，否则「拧参数看到变化」这件事就不可信了。

**推荐结构**（每个 `game.js` 都长这样）：

```js
// 1. 常量与配置（带注释说明每个数字的来源）
// 2. 状态（单一对象）
// 3. 纯函数：计算、判定（可单独推理，不碰 DOM）
// 4. 渲染：把状态画到页面
// 5. 交互：事件处理，只做「改状态 → render()」
// 6. 启动
```

**推荐结构**（每个 `walk.js` 都长这样）：

```js
// 1. 数据：提示词、候选表、场景常量（带注释说明哪些是真算的、哪些是示意）
// 2. 纯函数：softmax / 累计 / 判分（可单独跑，不碰 DOM）
// 3. 绘制辅助：vecStrip 这类本图解独有的画法（共享原语在 GameWalk.ui 里，不要重写）
// 4. steps 数组：每一步一个对象，字段见 ARCHITECTURE §6.8
// 5. GameWalk.mount({ id, params, steps })
```

图解最容易写坏的地方是第 2 步和第 4 步的边界：**任何在两个步骤里都出现的数字，必须由同一个纯函数算出来**。各步骤自己手写加法，第一次改参数就会露出「同一屏说 8972、另一屏说 9000」的矛盾。

### 4.2 CSS

| 项 | 要求 |
| --- | --- |
| 变量前缀 | 共享层 `--gh-*` / `--wk-*`；条目自有用缩写前缀，如 `--sp-*`（speculative）、`--tf-*`（transformer）、`--ag-*`（agent-loop） |
| 类名 | 小写 + 连字符（`.guess-row`）；状态类用 `is-` 前缀（`.is-active`、`.is-rejected`） |
| 布局 | flex / grid。**禁止** `float` |
| 断点 | 统一 `560px`；需要额外断点时在文件头注释说明理由 |
| 共享层 | 只用 `.gh-`（外壳）/ `.ghr-`（复盘面板）/ `.wk-`（图解外壳）前缀，**禁止**裸元素选择器 |
| 图解换色 | 想换高亮色只改自己 `:root` 的 `--wk-hit` / `--wk-hit-soft` / `--wk-hit-ink`，**禁止**改 `.wk-*` 类 |

### 4.3 HTML

- 语义标签：`header` / `main` / `section` / `button`。可点击的东西必须是 `button` 或 `a`，不是 `div`。
- 每个游戏页 `<title>` 与 `#gh-bar` 的 `data-title` 一致。
- 所有资源路径用相对路径（`../../shared/…`），因为站点部署在 `/game-hub/` 子路径下。

## 5. 注释

### 该注释什么

1. **文件头**：这个文件负责什么、不负责什么。
2. **为什么**：某个反直觉写法的原因（通常是踩过的坑）。
3. **魔法数字的来源**：`0.06` 是"每多验证一个 token 的边际时间"，不写清楚三个月后没人敢改。
4. **契约边界**：`#gh-help-source` 里必须是语义化 HTML 这类外部约束。

### 不该注释什么

```js
// ❌ 复述代码
i++;  // i 加一

// ✅ 解释约束
// 这里不能写成 i--：拒绝时要从被拒位置重新采样一个 token，
// 指针必须停在「待修正」的位置上，否则会跳过一格。
i++;
```

### 密度参考

- 200 行的游戏：8~15 条注释。
- 出现少于 3 条注释的文件，通常不是"代码自解释"，而是"没人想过为什么"。

## 6. 视觉与交互基线

新游戏必须和现有游戏观感一致，否则在大厅里并排看就是拼凑感。

### 尺寸

| 元素 | 值 |
| --- | --- |
| 主按钮 | 高 32~36px，圆角 9px，字号 13px |
| 卡片 / 面板 | 圆角 12~16px，内边距 16~20px |
| 正文 | 13~14px，行高 1.7~1.8 |
| 辅助文字 | 12px，颜色 `--gh-muted` |
| 数字 | 加 `font-variant-numeric: tabular-nums`，避免跳动 |

### 颜色

- 基线色一律取 `--gh-*` 变量，不要在游戏里重新定义一套黑白灰。
- **状态色不能只靠颜色区分**：接受用「✓ + 绿」，拒绝用「✗ + 红」。只给颜色，色觉障碍用户看到的是同一个灰块。
- 深色游戏（如贪吃蛇画布）自带画布配色，但面板、按钮、说明文字仍沿用浅色体系。

### 交互

- 每个操作必须有**即时反馈**（120ms 内）。超过 300ms 的操作要有进度提示。
- 状态变化用 `aria-live="polite"` 播报关键结果（回合结束、得分变化）。
- 键盘可达：所有按钮可 Tab 聚焦，`:focus-visible` 有可见轮廓。
- 破坏性操作（重开、清空）必须二次确认或用独立按钮，不能和主操作相邻。

## 7. 提交前自查清单

复制到 PR 描述里逐条打勾。

**文档**

- [ ] 游戏写了 `doc/games/<id>.md`（五段齐全）；图解写了 `doc/walks/<id>.md`（四段齐全）
- [ ] 图解文档里有一张「哪些数字是真算的、哪些是示意」的表
- [ ] 文档里的规则和代码实际行为一致（数值、判定、计分）
- [ ] `games.json` 的 `doc` 字段指向正确路径

## 9. 已踩过的坑

记录下来，避免重复踩。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| iframe 里也显示了「← 返回大厅」 | 作者样式的 `display:inline-block` 覆盖了 `[hidden]` 的 `display:none` | 显式写 `.xxx[hidden]{display:none}` |
| 改完 push，线上还是旧版 | GitHub Pages CDN `max-age=600` | 验证时加 `?v=<时间戳>`，或禁用缓存 |
| `file://` 打开是白屏 | 浏览器拒绝本地 `fetch('./games.json')` | 必须用 http 服务器 |
| 帮助弹层里按 Esc，游戏被一起关了 | 大厅的 Esc 监听与游戏内同时响应 | 共享层 `postMessage` 告知覆盖层状态 |
| 打开内容后按 Esc 完全没反应 | 大厅打开内容时 `focus()` 了 iframe，此后焦点在 iframe 内部，按键到不了父窗口 | `game-shell.js` 在弹层关闭时转发 `game-hub:escape`；页面想自用 Esc 就写 `data-esc="local"` |
| 两个游戏互相覆盖存档 | 都用 `localStorage` 裸键名 | 统一走 `GameShell.store('<id>')` |
| 数字宽度变化导致布局抖动 | 未使用等宽数字 | `font-variant-numeric: tabular-nums` |
| 四个游戏的复盘各写一份，很快就长得不一样 | 结构靠"自觉复制" | 抽成 `shared/review-panel.js`，结构由组件强制 |
| 复盘变成"把分数换个说法" | 只写判定和指标最省事，反事实最费事 | 反事实设为必填，组件缺项时页面上出红色告警 |
| 结束遮罩上的文字被棋盘压住 | 遮罩先 append 进棋盘，棋子后 append，同层后绘制的在上 | 给遮罩加 `z-index` |
| "同一开局换个策略"的数字没法比 | `Math.random()` 每次不同 | 种子 PRNG，把 seed 存进状态再传给对照策略 |
| 图解的四张指标卡竖着排成四行 | 每张卡各调一次 `ui.stat()`，各包了一个 `grid` | 一次传完整数组 `ui.stats(host, [...])`；要逐张加就用 `ui.statCard(grid, ...)` |
| 图解参数滑块拖不动，一拖就跳回去 | 拖 range 时重建了整个参数面板，把正在拖的节点换掉了 | 拖动时只重画画布、更新读数，不重建参数面板 |
| 图解某一步白屏，连导航一起没了 | `draw()` 抛错没兜住 | 外壳把绘制异常关在当前这一屏，显示红框，导航继续可用 |
| 图解里同一指标在两步显示不同数字 | 各步骤自己手写加法 | 抽一个 `cumulative(values, 上界)`，所有步骤只问「到这里为止多少」 |
| 图解默认为「摘要压缩」，最后一步总是缺点东西 | 默认参数恰好走在最有教育意义的那条坏路径上 | 这是有意的，但必须在那一屏给一句明确的出口：「把压缩策略改成 X 再看一次」 |
| 从游戏骨架复制图解，顺手带进了复盘面板 | 两个骨架长得很像 | `walk-shell.js` 检测到 `GameReview` 会在控制台告警 |
