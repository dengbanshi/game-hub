# 架构说明

> 这份文档是这个仓库的**地基层**。所有游戏都按这里的结构写，改动这里的任何约定都必须经过维护者审核（见 [§8 架构变更流程](#8-架构变更流程)）。
> 面向两类读者：新加入的贡献者（照 §6 的模板就能开工），以及半年后回来改代码的自己（解释「为什么当初这么设计」）。

---

## 1. 这个仓库要解决什么问题

一句话：**让人通过亲手操作，建立对某个大模型推理 / Agent 机制的直觉，并能用数字解释自己的决策代价。**

这个目标决定了三件事，下面所有设计都是它们的推论：

| 目标 | 推论 |
| --- | --- |
| 读者要能立刻玩到 | 打开链接就能玩，不能有安装、构建、登录 |
| 贡献者要能低成本加一个游戏 | 加游戏 = 加目录 + 加一条 JSON，不需要动框架 |
| 玩完要能说清「我为什么输」 | 每个游戏必须输出可归因的统计，而不是只给一个分数 |

## 2. 刻意的约束

这些不是「暂时没做」，是**明确不做**。违反了就等于换了个项目，请先读 §9 再说。

- **零构建**：没有打包器、没有 TypeScript 编译、没有 CI 构建产物。改一行 → `git push` → 生效。
- **零运行时依赖**：不用 React / Vue / 任何 npm 包。浏览器原生 API 足够。
- **零后端**：没有数据库、没有接口。存档只存本地。
- **每个游戏必须能独立打开**：`games/<id>/index.html` 直接访问也要完整可用，不能依赖大厅传参。
- **游戏之间零共享状态**：靠 iframe 隔离，样式、全局变量、事件互不影响。

## 3. 分层结构

```
┌──────────────────────────────────────────────────────────────┐
│ 大厅层（shell）                                                │
│   index.html   style.css   client.js   games.json             │
│   职责：读清单 → 渲染分类与卡片 → 用 iframe 装游戏              │
├──────────────────────────────────────────────────────────────┤
│ 游戏层（games/<id>/）                                          │
│   index.html（必需） + game.js / game.css / 数据文件（可选）     │
│   职责：这个游戏的全部玩法、渲染、计分                          │
├──────────────────────────────────────────────────────────────┤
│ 共享层（shared/）                                              │
│   game-shell.css   game-shell.js                              │
│   职责：顶栏、帮助弹层、存档命名空间、覆盖层通知                 │
├──────────────────────────────────────────────────────────────┤
│ 文档层（doc/）                                                 │
│   ARCHITECTURE.md   DEV-GUIDE.md   games/<id>.md              │
│   职责：架构、规范、每个游戏的知识与设计说明                     │
└──────────────────────────────────────────────────────────────┘
```

### 依赖方向：严格单向

```
大厅层  ──(只通过 URL 与 postMessage)──▶  游戏层  ──▶  共享层
```

- 游戏层可以依赖共享层（引入 `shared/game-shell.*`）。
- 共享层**禁止**知道任何具体游戏的存在。
- 大厅层**禁止**直接操作 iframe 内部 DOM。它只能：设置 `iframe.src`、发送 postMessage、接收 postMessage。
- 游戏层**禁止**访问 `window.parent` 的 DOM，只能 `postMessage`。

这条方向一旦反了（比如共享层里写 `if (gameId === 'snake')`），后面每加一个游戏都要改共享层，共享层就变成了第二个大厅。

## 4. 各层职责与红线

### 4.1 大厅层

**做**：读 `games.json`、渲染分类标签与卡片、搜索过滤、打开/关闭 iframe、维护 URL hash（`#agent` / `#inference` / `#game`）。

**不做**：任何游戏逻辑；任何具体游戏的样式；直接读写游戏的 localStorage。

判断标准很简单：如果一段代码里出现了某个游戏的名字，它就该在游戏层，不在大厅层。

### 4.2 游戏层

每个游戏是一个**自包含的独立页面**，唯一的外部依赖是共享层。

文件规模约定（见 `DEV-GUIDE.md`）：

| 规模 | 文件组织 |
| --- | --- |
| 逻辑 < 200 行 | 单文件 `index.html`，样式与脚本内联 |
| 逻辑 200 ~ 400 行 | `index.html` + `game.js` + `game.css` |
| 数据量大（题库、场景、参数表） | 再加一个纯数据文件，如 `scenario.js` |

数据文件必须是**纯数据**：只有 `const X = {...}`，没有 DOM 操作、没有副作用。这样别人想换个场景只需要改数据，不用读懂逻辑。

### 4.3 共享层

**只放**「所有游戏都要、而每个游戏各写一遍必定写歪」的东西。目前就四件：

1. 统一顶栏（返回大厅 + 帮助按钮）
2. 帮助弹层（内容来自游戏页的 `#gh-help-source`）
3. 带命名空间的 localStorage 封装
4. 覆盖层状态通知（让大厅的 Esc 不要顺手把游戏关掉）

**不放**：按钮样式、卡片样式、任何游戏特有的排版。共享层一旦开始长"通用 UI 组件"，就会有人为了一个特殊需求绕过它，最后两套样式并存。

**样式规则**：只用 `.gh-` 前缀的类名和 `--gh-` 前缀的 CSS 变量。这是硬性要求——2048 是浅色卡片、贪吃蛇是深色画布，共享层写一个裸 `button{}` 就会同时污染两边，而且这种冲突往往只有真机截图才看得出来。

### 4.4 文档层

每个游戏一份 `doc/games/<id>.md`，固定四段（顺序不许换，理由见 `DEV-GUIDE.md` §2）：

1. **背后的机制** —— 这个概念到底在解决什么问题
2. **能学到什么** —— 3~5 条，要具体到「你会亲眼看到 X」
3. **玩法规则** —— 操作、判定、计分
4. **代码设计** —— 数据结构、关键算法、为什么这么拆

## 5. 一次点击发生了什么

以「在大厅点开投机采样」为例，完整链路：

```
1. 用户点击卡片
   └─ client.js  openGame(g)
      · iframe.src = ./games/speculative/index.html
      · playerbar 显示标题、设计文档链接（GitHub blob）、新标签页链接

2. iframe 加载游戏页
   └─ 解析 <link shared/game-shell.css> → 拿到统一外壳样式
   └─ 解析 <script shared/game-shell.js> → 立即执行 boot()
      · mountBar()  往 #gh-bar 注入「← 返回大厅」（iframe 内隐藏）+「? 玩法与原理」
      · buildModal() 读取 #gh-help-source 的 HTML，构建弹层（此时不显示）
   └─ 解析 <script game.js> → 初始化棋盘/状态/事件

3. 用户点「? 玩法与原理」
   └─ shell 显示弹层，body overflow 锁死
   └─ 若在 iframe 内，postMessage {type:'game-hub:overlay', open:true}
      · 大厅收到后置 overlayOpen = true，此后 Esc 不再关闭游戏

4. 用户按 Esc
   └─ shell 在捕获阶段拦截：关弹层、阻止冒泡、postMessage open:false
   └─ 再按一次 Esc → 大厅收到（此时 overlayOpen 已为 false）→ 关闭游戏
```

关键点：**游戏页不需要调用任何初始化函数**。共享层在脚本加载时自动挂载。这样「忘记初始化」在结构上不可能发生——比在规范里写十遍"记得调用"可靠。

## 6. 契约

这一节是硬约定。改动任何一条都算架构变更，需要审核。

### 6.1 `games.json`

```json
{
  "schemaVersion": 2,
  "repo": "dengbanshi/game-hub",
  "categories": [
    { "id": "agent", "name": "Agent" },
    { "id": "inference", "name": "大模型推理" },
    { "id": "game", "name": "游戏" }
  ],
  "games": [
    {
      "id": "speculative",
      "name": "投机采样",
      "category": "inference",
      "version": "1.0.0",
      "contentCode": 1,
      "entry": "index.html",
      "doc": "doc/games/speculative.md"
    }
  ]
}
```

| 字段 | 必需 | 约定 |
| --- | --- | --- |
| `schemaVersion` | 是 | 当前 `2`。结构变动时 +1，大厅按版本兼容读取 |
| `repo` | 否 | `owner/name`，用于把 `doc` 拼成 GitHub 可读链接 |
| `categories[].id` | 是 | 小写字母。`all` 是保留字，不要占用 |
| `games[].id` | 是 | 小写 + 连字符，**必须等于目录名** `games/<id>/` |
| `games[].category` | 建议 | 必须是已声明的分类 id；漏写只会出现在「全部」里 |
| `games[].entry` | 是 | 入口文件名，目前统一 `index.html` |
| `games[].doc` | 是 | 相对仓库根的设计文档路径 |
| `games[].version` | 是 | 语义化版本 |
| `games[].contentCode` | 是 | 内容修订号；改了内容但版本号没变就 +1，用于区分 CDN 缓存 |

`id` 与目录名必须一致，因为大厅用 `./games/${id}/${entry}` 拼路径——不一致就会 404，而且是那种「本地看着好好的」404。

### 6.2 游戏页最小骨架

新游戏从这里复制。**不要删减**，缺哪个标签共享层会报警或降级。

```html
<!doctype html>
<html lang="zh-CN">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<title>游戏名</title>
<link rel="stylesheet" href="../../shared/game-shell.css">
<link rel="stylesheet" href="./game.css">
</head>
<body>

<header id="gh-bar" data-title="游戏名"></header>

<!-- 玩法正文，放在你自己的容器里 -->
<main class="wrap">…</main>

<!-- 帮助内容：给弹层读的，页面上不显示 -->
<div id="gh-help-source" hidden>
  <h3>这是什么机制</h3>
  <p>…</p>
  <h3>你能学到什么</h3>
  <ul>…</ul>
  <h3>玩法规则</h3>
  <ol>…</ol>
  <h3>算分方式</h3>
  <ul>…</ul>
</div>

<script src="../../shared/game-shell.js"></script>
<script src="./game.js"></script>
</body>
</html>
```

注意顺序：`game-shell.js` 必须在 `game.js` **之前**，因为游戏脚本可能要用 `GameShell.store()`。

### 6.3 帮助内容区块

`#gh-help-source` 的内容必须是语义化 HTML（`h3` / `p` / `ul` / `ol` / `code` / `strong`），不要带内联样式和 class——样式由共享层统一控制。

固定五段（第 5 段可选）：

| 段落 | 内容要求 |
| --- | --- |
| 这是什么机制 | 3~5 句说清它解决什么问题，不写论文摘要 |
| 你能学到什么 | 3~4 条，每条是「你会看到 X 导致 Y」而不是「了解 X」 |
| 玩法规则 | 编号步骤，包含失败条件 |
| 算分方式 | 公式或判定逻辑，要能让玩家自己验算 |
| 想深一点 | 1~2 个引导问题，指向这个游戏最反直觉的地方 |

这段内容和 `doc/games/<id>.md` 必须一致（弹层是精简版，文档是完整版）。改了一边忘了另一边，是这类项目最常见的腐烂方式——所以 `DEV-GUIDE.md` 把它列进了提交检查清单。

### 6.4 跨窗口消息

目前只有一条协议，未来要加必须先改本节：

```js
// 游戏 → 大厅
window.parent.postMessage({ type: 'game-hub:overlay', open: true }, location.origin);
```

| 项 | 约定 |
| --- | --- |
| 方向 | 只能是游戏 → 大厅 |
| 时机 | 任何覆盖全屏的弹层打开 / 关闭时 |
| 校验 | 大厅校验 `event.origin === location.origin` 且 `event.source === frame.contentWindow` |
| 用途 | 让大厅的 Esc 与游戏内的 Esc 不打架 |

大厅侧实现见 `client.js` 的 `message` 监听。没有这条协议，用户在帮助弹层里按 Esc 会连游戏一起关掉——这不是理论问题，是第一版就踩到的。

### 6.5 存档

```js
const store = GameShell.store('speculative');   // 实际键名 game-hub:speculative:<key>
store.set('best', 3.2);
store.get('best', 0);
```

- 命名空间 = 游戏 `id`。
- 禁止直接用 `localStorage.setItem`，否则键名冲突只能靠运气避免（所有游戏同源）。
- 旧游戏（2048 / 贪吃蛇）用的是 `game-hub-` 前缀，属于历史遗留，不强制迁移——迁移会让老用户的存档凭空消失，不如保留。

## 7. 什么是可变的，什么是不可变的

| 可以自由做 | 需要审核 |
| --- | --- |
| 新增游戏目录 + 清单条目 | 改动 `shared/` 里的任何行为 |
| 在已有分类下加游戏 | 新增分类 |
| 改某个游戏的内部实现、视觉、文案 | 改动 `games.json` 的字段结构 |
| 给游戏加新参数、新难度 | 新增跨窗口消息类型 |
| 补充文档 | 改动依赖方向、目录层级 |
| | 引入任何第三方依赖或构建步骤 |

一句话判断：**改动只影响一个游戏 → 自由；改动会影响所有游戏 → 审核。**

## 8. 架构变更流程

静态站点没有类型系统兜底，架构漂移不会报错，只会在半年后变成「没人敢动」。所以流程要求偏严：

1. **先改文档**：在本节下方的变更记录里加一行，说明动机、影响面、迁移方案。
2. **提交审核**：由维护者（仓库所有者）确认。未确认前不要合并到 `main`。
3. **全量回归**：所有游戏都要手动过一遍（大厅打开 → 帮助弹层 → 核心交互），因为共享层改动的影响面是"全部"。
4. **记录结果**：把回归结论写进变更记录。

## 9. 刻意的取舍

写给未来想推翻这些决定的人——先看看当年的理由是否还成立。

**为什么不用框架？**
单个游戏 300~600 行，状态就是几个数字和一个数组。框架带来的抽象成本（构建、依赖、约定）超过它省下的渲染代码。更重要的是：**零构建意味着改一行 push 就生效**，这对一个长期靠零碎时间维护的个人项目是决定性的。

**为什么用 iframe 而不是同页切换？**
样式、全局变量、事件监听全部隔离。代价只有一条 postMessage，而且协议被限制成一条消息，不算负担。如果改成同页渲染，第一个问题就是"两个游戏都定义了 `.board`"，第二个问题是"某个游戏忘了清理 `setInterval`"。

**为什么共享层这么薄？**
共享层越厚，遇到特殊需求时就越倾向于绕过它，最后变成"共享层 + 各写各的"两套并存，比一开始就不共享更糟。所以它只做那些"不做就一定会出错"的事：帮助入口、存档隔离、Esc 冲突。

**为什么帮助内容写在游戏页里，而不是单独的 md 文件？**
单独的 md 需要运行时解析（要么引入 markdown 库 = 破坏零依赖，要么写解析器 = 自找麻烦）。写在 HTML 里零成本，且离线可用。文档层另外保留完整版 md 给需要深读的人。

## 10. 目录总览

```
game-hub/
├── index.html              大厅入口
├── style.css               大厅样式（不含任何游戏样式）
├── client.js               清单读取、分类筛选、iframe 开关、消息监听
├── games.json              分类 + 游戏清单（唯一的数据入口）
├── .nojekyll               告诉静态托管别用 Jekyll 处理
│
├── shared/                 ← 所有游戏共用，改动需审核
│   ├── game-shell.css      顶栏 / 帮助弹层的样式（只用 .gh- 前缀）
│   └── game-shell.js       顶栏注入、帮助弹层、存档封装、覆盖层通知
│
├── games/                  ← 每个子目录 = 一个可独立打开的游戏
│   ├── g2048/              2048（存量，单文件）
│   ├── snake/              贪吃蛇（存量，单文件）
│   ├── speculative/        投机采样
│   │   ├── index.html
│   │   ├── game.css
│   │   └── game.js
│   └── context-window/     上下文窗口
│       ├── index.html
│       ├── game.css
│       ├── game.js
│       └── scenario.js     纯数据：场景与题库
│
└── doc/                    ← 文档即交付物的一部分
    ├── ARCHITECTURE.md     本文
    ├── DEV-GUIDE.md        开发规范
    └── games/
        ├── speculative.md
        └── context-window.md
```
